# 阶段 3：远程接入 设计

日期：2026-09-07
状态：3a 已实施并验证完成（2026-09-07）；3b 待细化
前置：阶段 2 已完成（三个前端共用一套核心，36 个测试全绿）

## 1. 形态：核心留在本机，增加远程入口

主设计文档原本的阶段 3 是「核心搬到服务器」。讨论后改为「**核心留在本机，增加远程入口**」。

```
形态 A（原计划，暂缓）   本机界面 ←网络→ 服务器上的核心     本机用法也要走网络
形态 B（现计划）        本机界面 ←本地→ 本机核心 ←网络→ 手机/网页
```

**理由：** 本机 GUI/TUI 是日常主力场景，不应为了远程而变复杂。形态 B 让本机路径保持简单，
远程是附加能力。

**形态 B 是通往形态 A 的必经之路**，不是绕路：WebSocket 传输层、网络桥接、断线处理、
跨网络的权限确认，两者都要。将来搬到服务器时做的是「把跑通的东西挪个位置」。

**触发重新考虑形态 A 的信号：** 本机电脑休眠导致连不上开始频繁困扰使用。

**服务器场景不为它做额外工作：** SSH + TUI 已经够用，安全性由 SSH 负责，比自造鉴权可靠。

## 2. 三个使用场景的归属

| 场景 | 归属 |
|---|---|
| 本机 GUI / TUI 日常用 | 已完成（阶段 1b / 2） |
| 在服务器上干活 | SSH + TUI，不额外开发 |
| 在外面用手机 / 网页 | **本阶段的唯一目标** |

## 3. 拆分：3a 与 3b

一次做完的话，出问题时无法判断是哪一块。沿用阶段 1 拆成 1a/1b 的做法。

**阶段 3a：本机拆分。** core-server + 客户端连接层 + GUI 改成客户端。
**全程只监听 `127.0.0.1`，没有任何网络安全面**，可以快跑。

**阶段 3b：网页界面与远程接入。** 构建步骤、共用界面代码、Tailscale、令牌、断线处理、
手机上的批准界面。到这一步传输层已被验证过，出问题只可能在新加的部分。

# 阶段 3a：本机拆分

## 4. 目标

把 Pi 从 Electron 主进程搬进独立的本机服务进程，GUI 改为通过 WebSocket 连接它。

**用起来必须和现在一模一样**——拆分不该让体验变差。这是本阶段最重要的约束。

## 5. 架构

```
                    ┌──────────────────────────┐
                    │ core-server（新）          │
                    │  ├ startCore() → Pi 子进程 │
                    │  ├ CoreClient + events     │
                    │  ├ session 账本 ← 唯一真相  │
                    │  └ ws 服务，127.0.0.1      │
                    └────────────┬─────────────┘
                                 │ WebSocket
                    ┌────────────▼─────────────┐
                    │ Electron 主进程            │
                    │  └ WebSocket ↔ IPC 中继    │
                    │ 渲染层（原样不动）           │
                    └──────────────────────────┘

TUI 不变：自己 startCore()，走 stdio，独立会话
```

**3a 里渲染层一行都不改。** 主进程从「养 Pi、管账本、经 IPC 发动作」变成「连服务器、
把收到的东西经同一套 IPC 转给渲染层」——**IPC 契约完全不变**，所以渲染层无感。

为什么不让渲染层直接连 WebSocket：那需要把 `core-client` 跑在浏览器里，而它是 `.ts`，
浏览器不认，**必须先编译**。构建步骤是 3b 的内容，3a 不引入。等 3b 做共用界面时，
渲染层会直接连服务器，`preload.js` 与 IPC 通道届时一并消失。

### 5.1 为什么 `session.ts` 这次必须用

阶段 2 的结论是「`session.ts` 服务于视图与状态之间有边界的架构」。**3a 把那道边界建回来了**，
而且比 GUI 的 IPC 更硬：

客户端可能**中途才连进来**（手机在对话进行到一半时打开），而已经流过去的事件追不回来。
所以服务器必须持有账本，新连接一上来先发一份完整快照，之后才推增量。

这是阶段 2 那条结论的正面印证，不是推翻。

### 5.2 线上协议

就是阶段 1b 那套 IPC 契约搬家。`main.ts` 里的 IPC 处理函数几乎原样变成服务器的消息处理函数。

**客户端 → 服务器**

```jsonc
{ "type": "prompt", "text": "..." }
{ "type": "abort" }
{ "type": "respond_confirm", "requestId": "...", "confirmed": true }
```

**服务器 → 客户端**

```jsonc
{ "type": "snapshot", "snapshot": { entries, totalTokens, totalCost, busy } }  // 连上时一次
{ "type": "actions", "actions": [ ...ViewAction ] }                            // 之后的增量
```

服务器把客户端来的消息一律当作不可信输入处理：校验类型与取值。

### 5.2.1 为什么不复用 `Transport` 抽象

`Transport` / `StdioTransport` 是为 **Pi 的 JSONL 协议**设计的——「一行行收发文本，不理解内容」。
而服务器与客户端之间说的是**另一套协议**（`prompt` / `actions` / `snapshot`），层级更高：
它携带的是已经折叠好的界面动作，不是 Pi 的原始事件。

所以客户端这侧新增 `RemoteSession`，与 `CoreClient` 并列而不是叠加：

```
core-server 内部：  CoreClient + StdioTransport  ──→ Pi（JSONL 协议）
客户端这一侧：      RemoteSession                ──→ core-server（本项目协议）
```

线上消息类型定义在 `core-client/src/protocol.ts`，服务器与客户端共用同一份，避免两边各写一遍
而慢慢对不上。

### 5.3 多客户端

同时连多个是**常态**（GUI 开着、手机也连着）。

- 动作广播给所有连接
- 任何客户端都能发命令
- 权限确认**谁先答谁算数**，之后到达的应答被忽略（`requestId` 已不在待答表里）
- 每个新连接独立收到一份快照

### 5.4 依赖形状

```
core-server → @cinba/core-host      startCore
            → @cinba/core-client    CoreClient / StdioTransport / events / session
            → ws                    WebSocket 服务端

core-client → 无依赖（保持）
              新增 protocol.ts（线上消息类型 + 校验）与 remote.ts（RemoteSession），
              用**原生 WebSocket**——浏览器、Electron 渲染层、Node 24 都内置，
              因此不引入任何依赖

desktop     → 不再依赖 core-host（Pi 不归它管了）
            → 仍依赖 core-client（主进程用 CoreClient + WebSocketTransport 连服务器）
```

**这解决了主设计文档第 8 节记录的待解问题**「`desktop` 同时扮演前端与核心侧」：
拆分后 `desktop` 只是前端，依赖规则回到设计原样。

`ws` 无安装脚本（2026-09-07 核实为 8.21.3），不改变仓库既有的安全姿态。

### 5.5 生命周期

**3a 里 core-server 手动启动**，一条命令。GUI 连不上时给出明确提示。

自动启动放到 3b。先让「关掉 GUI 服务还在」这件事简单地成立，而不是一上来就折腾进程守护。

端口固定 `127.0.0.1:4517`，只监听回环地址——**这是 3a 没有网络安全面的原因，必须守住**。

## 6. 安全（3a）

- 只监听 `127.0.0.1`，外部网卡不可达
- Electron 侧维持 `contextIsolation: true`、`nodeIntegration: false`、`sandbox: true`
- 权限门仍由 `core-host` 无条件挂载，不受本次拆分影响
- 渲染层来的消息在服务器侧校验类型

3a **不引入**任何对外监听、鉴权或加密——那些是 3b 的内容。

## 8. 3a 不做

网页界面、构建步骤、远程访问、鉴权、自动启动 core-server、断线重连。全部属于 3b。

## 8.1 备选项：让本机 TUI 也接 core-server（暂不做）

**现状：** TUI 自己 `startCore()` 起一个 Pi，走 stdio，会话与 GUI **不共享**。

```
GUI / 网页 / 旁观者  ──→ core-server ──→ Pi #1    共享同一个会话
TUI                 ─────────────────→ Pi #2    独立
```

**为什么这样：** TUI 的主场景是 SSH 到服务器上，那儿要的是「一个自包含的程序，跑起来就能用」，
不该要求先起一个服务；那台机器上也没有 core-server。

**改起来不难：** TUI 已具备 `RemoteSession`，改动约 30 行，加一个「连不上就自己起 Pi」的回退。

**为什么暂不做：**

1. 会引入一个新概念——「这个 TUI 是连服务器的还是独立的」。多一种模式就多一类困惑，
   而现在的规则很干净：TUI 永远独立。
2. 不确定这个用法真的会被用到。为想象中的需求加复杂度是划不来的。

**触发去做的信号：** 实际遇到「我在 TUI 里聊的，想在 GUI 里接着看」这种情况。那时是有依据的
决定，而不是提前铺路。

## 9. 3b 的意图（待 3a 完成后细化）

- **界面代码一套，GUI 与网页共用。** Electron 渲染进程本来就是浏览器，可以加载同一个页面，
  直接用 WebSocket 连服务器；`preload.js` 与 IPC 通道随之消失，主进程只剩「开窗口」。
  这一步需要构建步骤——`core-client` 要跑在浏览器里，而它是 `.ts`。
- **先做电脑屏幕的完整界面，之后再专门为移动端做适配设计。** 顺序如此是因为大屏上先把功能与
  信息层级理清楚，移动端才知道该砍什么。
- **一个例外，属于安全而非美观：** 批准工具调用的界面从第一天起就必须在手机上看得清。
  用户在外、小屏、注意力分散，而按下去的后果是在自己电脑上执行命令——「这条命令是什么」
  必须一眼看明白，不能需要横向滚动才读得完。
- **远程通道用 Tailscale 这类私有网络**，本机不开放公网端口。安全性从「我写的代码够不够好」
  变成「我配置对了没有」。在此之上仍加应用级令牌作纵深防御。
- **明确不做：** 把服务直接暴露在公网上——哪怕加了密码。这个服务的权限是完整 shell，
  风险与收益不成比例。
