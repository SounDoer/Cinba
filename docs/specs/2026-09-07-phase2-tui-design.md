# 阶段 2：TUI 设计

日期：2026-09-07
状态：已实施并验证完成（2026-09-07）
前置：阶段 1b 已完成（Electron GUI 可日常使用，33 个测试全绿）

## 1. 目标

做一个能在终端里日常使用的客户端，主要场景是 SSH 到服务器上用。

同时它是**对阶段 1b 架构决策的检验**：`events.ts` 与 `session.ts` 当初放进 `core-client`
而不是 Electron 主进程，理由就是「换个前端能原样复用」。阶段 2 给出答案。

## 2. 范围

**做：**

- 多轮连续对话，流式输出
- **固定输入框**：输出滚动时不冲掉正在输入的内容
- 工具调用显示，三种状态：待批准 / 完成 / 被拒

  GUI 有第四种「执行中」，但那是 Electron 主进程在用户点允许后**自己补发**的
  （`createEventFolder` 从不产生 `running`——Pi 在确认与执行完成之间不发任何事件）。
  TUI 没有那个补发环节，也不需要：确认框消失本身就是「开始执行了」的信号。
- 权限确认：用选择列表选「是 / 否」
- 底部状态栏：累计 token 与费用
- `Esc` 中止当前回答，`Ctrl+C` 退出并回收 Pi 子进程

**不做**（沿用主设计文档第 7 节「阶段 2 刻意做朴素」）：模型选择器、会话浏览、
会话分叉、thinking 显示、Markdown 渲染。

**工作目录 = 启动时所在目录**，不做切换。终端里 `cd` 到哪就在哪开工是自然行为；
再做一个选择器反而别扭，也顺带避开了主设计文档第 8 节记录的「共享文件系统」那个坑。

## 3. 技术选型

### 3.1 用 pi-tui

`@earendil-works/pi-tui`，Pi 自带的终端 UI 工具箱。它是纯界面库，不含 agent 逻辑，
地位相当于 React——因此不违反主设计文档第 5 节「前端不依赖 Pi」（那条挡的是
`pi-coding-agent` 本体）。

**为什么需要一个 TUI 库而不是 `readline`：** 终端不像浏览器那样自带 DOM 与渲染引擎。
`readline` 是「打字机模型」——输出和输入共用同一个光标，流式输出会直接写在用户正在
输入的那一行上，把它冲花。这不是能靠技巧绕过的，是模型本身的限制。TUI 库提供「白板模型」：
接管屏幕、每次变化整体重绘，输出区与输入框是两个区域，天然不打架。

「一边看模型输出、一边打下一句」是日常使用的基本盘，所以这一点不能妥协。

**为什么是 pi-tui 而不是 Ink：** Ink（终端里的 React，Claude Code 与 Codex 都在用）
文档更全、生态更大，但对本仓库有一项硬成本——JSX 必须编译，而本仓库的一条性质是不编译
（Node 24 的类型剥离只做「擦除」，JSX 需要的是「变形」，原理上做不到）。用 Ink 就得
引入构建步骤，或者放弃 JSX 手写 `createElement`（可读性优势随之消失）。

pi-tui 这边则有两项现成的东西：Markdown、多行编辑器、选择列表、图片显示等对口组件已经
齐备；且 Pi 自带一个 641 行的官方 RPC 客户端示例（`examples/rpc-extension-ui.ts`），
做的事与我们几乎一致，在缺少文档的情况下可作参照。

### 3.2 已知代价与将来的换法

pi-tui 没有公开文档、版本跟随 Pi 发版、使用者少。这些风险被限制在**一个文件**里：
`pi-tui` 只出现在 `packages/tui/src/index.ts`，其余四个包都不知道它存在。

**将来的方向（阶段 4 打磨期再定）：** GUI 侧可能引入前端框架，TUI 侧可能换成 Ink。
届时引入构建步骤的理由会比现在充分（大概率不止一处需要），且那时对两个界面都已有实感，
更清楚要什么。换 TUI 的成本是重写单个文件，约 200 行，`events.ts` 那层不受影响。

现在不提前做，是因为**为了一个界面库去改整个仓库「不编译」的性质，代价与收益不成比例**。

## 4. 架构

### 4.1 复用哪些、不复用哪些

```
core-host     ✅ 原样复用（startCore 自带权限门）
core-client
  ├ transport ✅ 原样复用
  ├ client    ✅ 原样复用
  ├ events    ✅ 原样复用  ← 这是跨前端复用的核心
  └ session   ❌ 不用       ← 见下
extensions    ✅ 原样复用
```

**`session.ts` 不用，是有意的。** 它解决的问题是「视图与状态之间隔着一道边界，视图需要
随时能整份重建」：GUI 里那道边界是 IPC（刷新窗口后靠快照恢复），阶段 3 的网页版会是
WebSocket。**TUI 是单进程，没有那道边界**，终端里也没有「刷新重建」这回事——画过的内容
滚上去就固定了。

实际做法比预想的还简单：TUI 的输出区是**纯追加式**的一列文本行，连 Map 都不需要。
唯一的可变状态是「正在流式输出的那一行」，靠 `Transcript.appendInline` 往最后一行接就够了。
工具状态变化也用追加表达（先一行「待批准」，完成后再追加「✅ 完成」），而不是原地改写——
`TuiMainScreen` 只能重画还在可视区域内的行，滚上去的改不动。

**这构成阶段 2 的第一个结论：**

> `events.ts` 是真正跨前端复用的那一层。`session.ts` 的适用范围更窄——它服务于
> 「视图与状态之间有边界」的架构。这不是抽象做错了，是它的适用面比原先设想的小。

若实施过程中发现 TUI 其实也需要账本（例如某种重绘场景），说明上述判断有误，
应回来修正本节而不是硬扛。

### 实测结论（2026-09-07）

**判断成立。** TUI 全程未使用 `session.ts`，也未使用 `foldUiRequest`；`createEventFolder`
原样复用，一行没改。TUI 需要的「状态」只有一个正在流式输出的当前行，靠 `Transcript.appendInline`
就够了，不需要账本。

`foldUiRequest` 同理：它把 UI 请求包装成一个可跨边界传输的动作，而 TUI 拿到 `UiRequest`
就能直接用。

**但检验也暴露了抽象漏掉的一块。** `events.ts` 原先只把 `agent_settled` 折成
`busy_changed: false`，没有对应的 `true`——于是每个前端都得在发送时自己补一句。GUI 补过，
TUI 起初漏了，症状是 Esc 中止完全失效。已改为 `agent_start` 也折成 `busy_changed: true`，
前端忘了补只会慢一拍，不会坏掉。

**这正是「用第二个前端检验抽象」的价值**：只有一个前端时，它自己补的那句话看起来天经地义，
根本看不出是抽象缺了一块。

### 4.2 依赖形状

```
packages/tui → @cinba/core-client        （events.ts、CoreClient、StdioTransport）
             → @cinba/core-host          （startCore）
             → @earendil-works/pi-tui    （纯界面库）
```

与 `packages/desktop` 同形。`tui` 同时扮演前端与核心侧，这与主设计文档第 8 节记录的
`desktop` 的情况一致，属同一项待解问题，不另开一条。

### 4.3 界面布局

```
┌──────────────────────────────────┐
│ 你：帮我看看 package.json          │  输出区，向上滚动
│                                  │
│ 助手：好的                         │
│ 🔧 read  待批准                    │
│    {"file":"package.json"}        │
│    → [是] [否]                     │  SelectList
├──────────────────────────────────┤
│ > _                              │  输入框，钉在底部
│ 2041 tokens · $0.0009      Esc 中止│  状态栏
└──────────────────────────────────┘
```

权限确认期间，底部由输入框临时换成选择列表；选完换回。这是 Pi 官方示例的做法，直接沿用。

## 5. 安全

权限门由 `core-host` 无条件挂载，TUI 侧无需也无法关闭（阶段 1b 收尾时的决定）。

TUI 对模型输出不做任何富文本解析（本阶段不渲染 Markdown），因此没有 GUI 侧那类注入面。

## 9. Windows 全局命令（2026-09-13）

TUI 改为连接常驻 Core 后，本机的自然入口应当是：先 `cd` 到项目，再直接输入 `cinba`。根包通过
标准 npm `bin` 声明把 `cinba` 指向 `scripts/cinba.ts`；用户在仓库中执行一次 `npm link`，npm 就会
在已经位于 `PATH` 的全局命令目录生成 Windows shim，并把它链接回当前 checkout。

入口链为：

```text
任意 PowerShell 目录中的 cinba
→ npm 管理的全局 Windows shim
→ scripts/cinba.ts
→ scripts/launch.ts tui <当前目录>
→ packages/tui/src/index.ts
```

`scripts/cinba.ts` 只负责把当前目录和 `tui` mode 交给共享 launcher，不复制端口检查、子进程管理或
TUI 启动逻辑。npm link 也不复制仓库文件，所以 checkout 更新后全局命令自动使用新代码；仓库移动
后重新执行 `npm link` 即可。卸载使用 `npm unlink --global cinba`。

原有的 Web/Core 双击入口从 `cinba.cmd` 明确改名为 `cinba-web.cmd`；开发入口继续是
`cinba-dev.cmd`，支持拖拽项目目录的 TUI 入口继续是 `cinba-tui.cmd`。因此 `cinba` 在 PowerShell
和传统 `cmd.exe` 的任意目录中都只表示全局 TUI 命令，同时三个 `.cmd` 文件仍保留各自清楚的双击
用途。

### 9.1 统一产品入口更新（2026-09-14）

随着 `cinba core ...` 等子命令出现，`scripts/cinba.ts` 已从 Windows 专用薄入口升级为统一产品
CLI。它现在直接调用 `scripts/launch.ts` 导出的 `launchTui()`，不再改写 `process.argv` 后动态导入
launcher。`cinba-tui.cmd` 也先进入 `scripts/cinba.ts`；平台入口只负责让操作系统找到命令和提供
默认项目，产品命令只解析一次。
