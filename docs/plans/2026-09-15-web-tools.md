# Web tools 实施计划

日期：2026-09-15
状态：代码实施完成；自动化验收通过；真实 Provider 人工验收仍按阶段 10 执行
对应设计：`docs/specs/2026-09-15-web-tools-design.md`
调研记录：`docs/notes/2026-09-15-web-tools-probes.md`

## 目标与完成标准

把已经确认的联网设计落成一套与模型无关的 Pi extension：

- 模型获得 `web_search` 和 `web_fetch` 两个工具；
- 搜索按配置在 Exa、Brave 和 DuckDuckGo 之间路由与降级；
- 任意网页读取经过 SSRF 防护、正文提取和 Markdown 转换；
- Web 与 TUI 都能查看状态、管理 Exa/Brave key、选择搜索首选项；
- Stable、Dev 和 VPS 使用各自 Core 的 state directory，不共享落盘配置；
- 密钥不进入仓库、日志、服务端响应、工具结果或测试快照；
- `npm run check` 全量通过，并用 Dev Core 完成一次真实 Provider 验收。

第一版不做浏览器渲染、登录网页、PDF、SearXNG、搜索历史、配额统计、Provider 高级参数和
产品 CLI 子命令。

## 实施原则

1. 先做能够用纯本地测试证明的存储和网络底座，再接外部 Provider。
2. extension 只负责模型工具；配置管理由 Core 协议负责，客户端不直接读写文件。
3. 固定 Provider API 与用户任意 URL 使用两条网络路径。前者可用 `fetch`，后者必须在实际建连时
   校验并固定 DNS 结果，不能用“预解析一次，再让 `fetch` 重新解析”的伪防护。
4. `web_fetch` 的第三方解析库只在首次调用时动态加载。
5. 自动测试不用真实 key、不依赖公网，也不把 DuckDuckGo 页面结构当成稳定契约；真实请求留到
   最后的人工 Dev 验收。
6. 每个阶段先运行该 package 的小范围测试；跨 package 接通后再运行完整 merge gate。

## 阶段 2：配置与凭据存储

### 普通配置

扩展 Core 现有的 `<CINBA_STATE_DIR>/config.json`，增加：

```json
{
  "webSearchPrimary": "auto"
}
```

合法值只有 `auto`、`exa`、`brave`。缺失或非法时读为 `auto`；写回时保留文件里的其他已知配置。

### 密钥文件

新增 `<CINBA_STATE_DIR>/credentials.json`，第一版内部形状为：

```json
{
  "webTools": {
    "exa": { "apiKey": "..." },
    "brave": { "apiKey": "..." }
  }
}
```

存储层分成两类接口：

- extension 使用的 secret reader：只按指定 Provider 取当前有效 key；
- Core 管理接口使用的 redacted reader/writer：只暴露是否配置、有效来源和是否存在落盘 key。

读取优先级为环境变量高于落盘 key。删除操作只删除落盘 key；若环境变量仍存在，Provider 仍显示
可用，同时状态明确 `source: "environment"`、`hasStoredCredential: false`。

写入采用同目录临时文件加原子 rename。支持的平台上将目录权限设为 `0700`、文件权限设为
`0600`；Windows 依赖用户目录继承 ACL，不声称 POSIX mode 是 Windows 安全边界。写入时保留未知
顶层字段，为以后其他 extension 共用凭据文件留空间。

凭据文件缺失等同于没有 key；凭据文件内容损坏则 fail closed，报告错误并拒绝覆盖，避免一次设置
操作悄悄抹掉其他秘密。

### 测试

- config 缺省、合法值、非法值、更新后保留其他字段；
- credentials 缺失、读取、替换、删除、保留未知字段；
- 环境变量覆盖落盘 key，但状态仍能表达是否有 stored key；
- 写入不把 key 返回给调用者；
- 损坏 JSON 不被覆盖；
- 原子写入后不遗留临时文件；支持的平台检查 mode。

### 完成条件

所有测试只使用临时 state directory；测试输出和 snapshot 中没有示例 key 的完整文本。

## 阶段 3：任意 URL 的安全 HTTP 传输

在 `packages/extensions/src/web-tools/` 中实现独立的安全传输层，暂不做正文解析。

### URL 与地址规则

- 只接受 `http:`、`https:`；
- 拒绝 URL userinfo、无效端口和非标准主机形式；
- 拒绝 `localhost`、本机名以及 loopback、private、link-local、CGNAT、multicast、unspecified、
  documentation、benchmark、保留地址和云 metadata 地址；
- 同时处理 IPv4、IPv6、IPv4-mapped IPv6 和 DNS 返回多个地址的情况；
- DNS 返回的任一地址不安全时，整次请求拒绝，而不是从中挑一个“看起来安全”的地址；
- 每一次 redirect 都重新执行完整 URL、DNS 和地址检查。

### 建连方式

使用 Node `http`/`https` 和自定义 `lookup`：先解析并检查，然后把已经批准的地址交给本次 socket
连接。HTTPS 仍以原 hostname 做 SNI 和证书校验。这样 DNS 检查与真正连接使用的是同一个结果。

### 资源边界

- 一个总 deadline：20 秒；redirect 不重置；
- 最多 5 次 redirect；
- 支持 `gzip`、`deflate`、`br`；
- 对解压后的字节计数，达到 2 MiB 后停止读取并标记 `downloadTruncated`；
- 不发送 Cookie、Authorization 或搜索 Provider key；
- 只接受后续解析层支持的文本 MIME；二进制类型给出清楚错误；
- 将调用方 `AbortSignal` 一直传到底层 socket；用户取消与超时使用不同错误分类。

### 测试

使用本地 HTTP/HTTPS fixture server 和可注入 DNS lookup，覆盖：

- public address 成功、private/loopback 拒绝；
- 多地址中混入 private 地址时拒绝；
- IPv4-mapped IPv6 绕过失败；
- public URL redirect 到 private URL 时拒绝；
- redirect loop、超过次数、相对 Location；
- 总 deadline 不会被 redirect 重置；
- gzip/deflate/br 解压后超限；
- 调用方 abort 立即关闭请求；
- hostname、Host header、SNI 与证书验证没有被固定 IP 破坏。

### 完成条件

安全性由确定性的本地测试证明；没有任何“先 DNS 检查、后由另一套 resolver 建连”的窗口。

## 阶段 4：`web_fetch` 内容提取

### 处理管线

1. 安全传输层取得最终 URL、响应头和受限字节流；
2. 按响应 charset 解码支持的文本内容；
3. `text/html` 首次使用时动态 import `jsdom`、Readability 和 Turndown；
4. JSDOM 不执行 script、不加载图片、样式、iframe 等子资源，并以最终 URL 解析相对链接；
5. DOM 元素超过 50,000 时停止重型提取并返回明确错误或轻量降级结果；
6. Readability 提取正文；失败时使用经过清理的 `body` 文本作为有限降级；
7. Turndown 转为 Markdown，Cinba 薄适配统一链接、图片、代码块、空白和无关元素；
8. 使用 Pi 的 `truncateHead` 和默认限制输出 50 KiB / 2,000 行。

`text/plain` 和其他明确支持的文本类型跳过 DOM 管线。结果 `content` 面向模型阅读；`details` 只含
最终 URL、标题、内容类型、正文、`downloadTruncated`、`outputTruncated` 等类型化数据，不含响应
header、Cookie 或内部错误对象。

### 测试

- HTML 正文、标题、相对链接转绝对链接、代码块、列表；
- script 不执行、子资源不请求；
- Readability 失败降级；
- plain text；
- 不支持 MIME；
- 50,000 元素边界、下载截断、模型输出截断分别可区分；
- 恶意 HTML 中的 prompt injection 只是普通网页文本，不改变工具协议或渲染为 HTML。

### 完成条件

fixtures 能覆盖提取行为；从未调用 `web_fetch` 时，Pi 子进程不会加载三个 DOM/转换依赖。

## 阶段 5：搜索 Provider 与路由器

### 标准结果

三家 adapter 统一输出：

```ts
type WebSearchResult = {
  title: string;
  url: string;
  snippet: string;
};
```

只在可靠时增加可选元数据，不把 Provider 原始 JSON 暴露给模型。

### Provider adapter

- Exa：`POST https://api.exa.ai/search`，`x-api-key`，请求有限数量结果与 highlights；
- Brave：`GET https://api.search.brave.com/res/v1/web/search`，`X-Subscription-Token`，普通 Web
  Search，并发送已验证的 API version；
- DuckDuckGo：请求公开 HTML 页面，解析结果链接、标题和摘要，解开 `uddg` 跳转参数。challenge、
  页面结构无法识别、没有任何可识别的结果容器均算技术失败；真正可识别的零结果才算成功。

固定 Provider endpoint 可以用 Node `fetch`，但每家单次最多 8 秒、响应最多 1 MiB、不自动重试。
错误转换为内部分类：认证、限流、超时、网络、上游状态、响应过大、格式错误。

### 路由

- `auto` / `exa`：Exa → Brave → DuckDuckGo；
- `brave`：Brave → Exa → DuckDuckGo；
- 没有 key 的付费 Provider 直接跳过；
- 技术失败才尝试下一家；有效零结果立即返回；
- 总 deadline 20 秒；每家 8 秒受剩余总时间约束；
- 用户 abort 立即结束，不触发降级；
- 不跨调用记忆“Provider 不健康”，避免一次故障污染后续 session。

最终成功结果可以附带经过脱敏的降级 warnings，例如 `Exa authentication failed; used Brave`；所有
Provider 都失败时返回聚合后的短错误，不含 key、完整响应 body 或 header。

### 测试

- 每家正常响应、空结果、畸形响应、超限、超时和错误状态；
- query trim、非空、最多 600 字符与 75 词；`max_results` 默认 5、范围 1–10；
- 不同 primary 的顺序、缺 key 跳过、技术失败降级、零结果不降级；
- 用户 abort 不降级；总 deadline 生效；
- warnings 与聚合错误不会泄露 Authorization header 或 key。

### 完成条件

所有 adapter 使用注入的 transport 和 fixture 响应完成测试，正常测试套件不访问公网。

## 阶段 6：Pi extension 注册与权限策略

### 注册

- 新建 `packages/extensions/src/web-tools.ts` 作为 extension 入口；
- 具体代码放在 `packages/extensions/src/web-tools/`；
- 注册 `web_search`、`web_fetch`，提供 JSON schema、`promptSnippet` 和 `promptGuidelines`；
- `web_search` 每次调用重新读取当前 config/credentials；`web_fetch` 不读取凭据；
- 并行调用互不共享可变状态，完整传播 Pi 传入的 `AbortSignal`；
- 更新 `packages/agent/src/pi-process.ts`，让每个 Pi 子进程都加载 web-tools extension。

### 权限

在 permission gate 中将两个工具列为 Cinba 内置只读工具并自动允许。`web_fetch` 的 URL 安全判断不
属于可交互权限：危险地址必须硬拒绝，不能让用户点击 Allow 绕过。

### 测试

- fake Pi 捕获两个工具的注册信息，断言 schema、snippet、guidelines 和执行结果；
- 修改临时配置后，下一次 search 立即使用新值；
- agent 启动参数包含 web-tools；
- permission gate 对两个工具不弹确认，对未知工具行为不变；
- extension 的 content/details 都不含秘密。

### 完成条件

一个不支持原生联网的模型也能在 Pi 层看见两个工具；工具描述明确提醒网页内容不可信、搜索后需要
fetch 来源正文。

## 阶段 7：Core 协议与共享客户端

### Contract

在 `packages/contract` 增加精确的公共类型：

```ts
type WebSearchProviderId = "exa" | "brave" | "duckduckgo";
type WebSearchCredentialProviderId = "exa" | "brave";
type WebSearchPrimary = "auto" | "exa" | "brave";

type WebSearchProviderStatus = {
  id: WebSearchProviderId;
  name: string;
  available: boolean;
  source?: "environment" | "stored";
  hasStoredCredential: boolean;
  bestEffort: boolean;
};

type WebToolsStatus = {
  primary: WebSearchPrimary;
  effectiveOrder: WebSearchProviderId[];
  providers: WebSearchProviderStatus[];
};
```

DuckDuckGo 的 `hasStoredCredential` 固定为 false、`bestEffort` 为 true。若 UI 需要表达两个工具始终
存在，可在状态中增加不含可变语义的 capability 字段，但不引入假的 enabled 开关。

新增 client messages：

- `get_web_tools_status`
- `set_web_tools_api_key`
- `clear_web_tools_api_key`
- `set_web_search_primary`

新增 server message：`web_tools_status`。Provider id 和 primary 在协议入口做严格 validation；key 只
允许从 client 到 server，任何 server message 都没有 key 字段。

### Server 与 core-client

- Core 通过存储层读取/修改本 Core 的 state directory；
- `get` 只回复请求者；修改成功后向已连接客户端广播最新脱敏状态；
- API key 做 trim 后必须非空；clear 只作用于 stored key；
- 本地与远程已认证客户端能力一致，不重新加入 loopback 写入限制；
- `packages/core-client` 暴露对应方法和 status callback，Web、TUI、Desktop 不自行拼协议消息。

如果 `packages/server` 直接 import extensions 的存储模块，需要在其 `package.json` 添加显式
`@cinba/extensions` workspace dependency，不能依赖 hoisting 偶然可见。

### 测试

- protocol parser 接受全部合法消息，拒绝未知 Provider、非法 primary、空 key 和多余危险字段；
- core-client 方法编码正确，status callback 解码正确；
- server get/mutate/broadcast、环境变量优先和损坏凭据文件错误；
- 每个消息对象序列化后都不含已保存 key。

### 完成条件

管理功能完整穿过 `core-client`；三个客户端未来都只依赖同一份状态类型和同一组操作。

## 阶段 8：TUI 功能版

在共享 command registry 中增加 `/webtools`，只保留一个顶层命令，打开交互式管理 flow。

首次进入先请求最新状态，菜单提供：

- View status：显示 primary、effective order，以及 Exa/Brave 的配置来源；DuckDuckGo 标为
  best-effort fallback；
- Add or replace API key：选择 Exa/Brave，使用不回显的 secret input；
- Remove stored API key：只列出 `hasStoredCredential` 为 true 的 Provider，并说明环境变量不会被
  删除；
- Choose primary：选择 Auto、Exa 或 Brave，随后显示实际 effective order。

从现有 provider flow 提取可复用的 choice dialog 和 secret input，避免复制一套键盘、取消和遮罩
逻辑。请求进行时阻止重复提交；服务端错误显示在 flow 内，退出后不残留 key 文本。

### 测试

- command registry 与 `/webtools` 分派；
- 各 action 的状态转换、cancel、错误与成功刷新；
- password 输入不出现在 render snapshot；
- stored 与 environment source 的文案正确。

### 完成条件

用户可以只在 TUI 内完成查看、配置、清除和切换，不需要知道 credentials 文件位置。

## 阶段 9：Web / Desktop 功能版

沿用现有 Provider settings 的轻量 overlay 形态增加 Web tools settings，不在此阶段重构布局。Desktop
复用同一 Web UI，因此不做第二套管理页面。

页面显示：

- 搜索首选项与实际降级顺序；
- Exa、Brave 是否可用、来源是 environment 还是 stored；
- DuckDuckGo 的 best-effort 提示；
- Add/replace 和 Remove stored key；
- `web_fetch` 不需要 key 的说明。

password input 提交后立即清空，永不把已有 key 回填到 DOM。请求进行时 disable 对应操作，状态以
Core 返回值为准，不做乐观伪成功。

### 测试

- `use-core` 暴露状态和四个管理操作；
- overlay 的打开、关闭、设置 primary、写 key、删 key 和错误反馈；
- DOM、测试快照和 console 不出现 key；
- Core 广播后另一个已连接客户端同步状态。

### 完成条件

`npm run dev` 启动后能在 Web 功能版中完成所有管理操作；Desktop 自动获得相同能力。

## 阶段 10：端到端与真实验收

### 自动 E2E

用临时 `CINBA_STATE_DIR` 启动真实 Core/客户端流程，验证：

- 设置 Exa/Brave key 后写入该 state directory 的 `credentials.json`；
- status、WebSocket 帧的 server 方向、日志和终端输出不含 key；
- clear 删除 stored key 且保留其他字段；
- Stable 与 Dev 指向不同目录；Dev 不继承通用 key；
- 配置 primary 后重启 Core 仍然有效；
- Web 与 TUI 对同一个 Core 的状态一致。

不要在 E2E 中访问真实搜索服务。工具网络行为已经由 fixture/injected transport 测试覆盖。

### 人工 Dev 验收

在前述自动测试通过后，由用户在 Dev Web UI 中输入自己的 key；key 不写进命令、fixture 或聊天记录。
依次验证：

1. Exa 成功搜索；
2. Brave 成功搜索；
3. 临时清除/使用无效首选 key 后，技术失败会降级且 warning 可读；
4. 两个付费 key 都不配置时，DuckDuckGo 能 best-effort 返回；
5. 从搜索结果调用 `web_fetch` 能得到正文 Markdown；
6. private/localhost URL 被硬拒绝；
7. 切换模型后仍看到完全相同的两个工具。

验收完成后删除为了测试而存入 Dev 的无效 key。有效 key 是否保留由用户决定。

### 最终检查

```bash
npm run check
```

同时人工搜索仓库 diff、测试输出和日志，确认没有 key 或临时抓取页面进入版本控制。

## 风险检查点

开工后在以下节点停下来复核，而不是等最后一起排错：

- 安全 HTTP 层完成后：专门审查 DNS rebinding、redirect 和解压后大小限制；
- Provider router 完成后：专门审查“零结果不降级”和 abort 不降级；
- Contract 完成后：确认 Web、TUI、Desktop 三端同步，server message 无 secret 字段；
- UI 完成后：检查 password input、console、错误消息和 snapshot 均不泄密；
- merge gate 前：确认 Dev 环境变量隔离不会误伤 Stable/VPS 启动。
